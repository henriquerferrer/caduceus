# F1 audit

### 1. A Verify handler's full-row write can overwrite a stored expiry, so an 'expired' verification goes back to 'pending' or becomes 'approved'
severity: low
lens: correctness
refuted_votes: 0/3
proven: confirmed
converged: data-integrity (original block 3, "Verify handlers' whole-row writes can overwrite an expiry stored concurrently by the unlocked REST read path") reported this same defect independently; two lenses, one block
disposition: followup F1.7

file: internal/server/server.go:358-374 (unlocked REST reads); internal/store/verification.go:133-136 (unconditional UpdateVerification); internal/server/verify.go:316-334

`GET /api/v1/verifications` and `GET /api/v1/verifications/{sid}` apply and store expiry without taking `verifyMu`. The Verify handlers take `verifyMu`, read the verification, then write it back with `UPDATE ... WHERE id = ?` and no condition on status. If the TTL ends between a handler's read and its write, and an unlocked REST read stores `expired` in that window and publishes an `expired` event, the handler's write then replaces `expired` with the status it read earlier. verifyCheck writes `pending` (with one more check attempt) or `approved`, verifyStart's resend writes `pending`, and verifyUpdate writes `canceled` or `approved`. A terminal `expired` state is therefore published and then undone. This contradicts the `verifyMu` comment in server.go:49-52 ('serialises every Verify read-modify-write') and F1.2's design ('Every handler holds verifyMu across its reads and writes ... because a read can store an expiry'). F1.1 only protects the opposite direction: the expiry write cannot overwrite a check.

### 2. F1's new verification routes are served with no Host or Origin check, so a DNS-rebinding page can read live codes (already tracked)
severity: low
lens: authz
refuted_votes: 0/3
proven: confirmed
disposition: blocked F1.8

file: internal/server/server.go:117

No code in F1 checks the Host or Origin header on any route of the local mux. The code-bearing reads added by F1 can therefore be read by a page whose hostname rebinds to 127.0.0.1. These are GET /api/v1/verifications, GET /api/v1/verifications/{sid}, and `verification` events on GET /api/v1/events. All of them include the plaintext `code`. The same missing check lets any cross-site page send CORS-simple POSTs to the new write routes: POST /api/v1/verifications/{sid}/expire (no body needed), POST /v2/Services/{service}/Verifications/{sid} (form body, Status=approved|canceled) and POST /v2/Services/{service}/VerificationCheck. The write routes are only practically abusable when the page knows the service SID and the VE sid, which it cannot learn cross-origin without the rebinding read. This is the one place where a party outside the trust boundary reaches F1 data. It is not new: roadmap/discovered/archive/local-rest-api-has-no-origin-or-host-check-90b0f3.md records it, and F1 widened an exposure that already existed.

### 3. Inbox load() can drop a verification an SSE event just delivered, so its badge loses its status (the newer() guard only covers verifications that are in the list)
severity: low
lens: concurrency
refuted_votes: 0/3
proven: confirmed
disposition: followup F1.9

file: internal/server/ui/index.html:95-99

When a load() that started before a Verify send finishes after a later load(), it replaces the whole `verifications` map with the older list. Any verification created after that list was read, and already added from its SSE `verification` event, is removed. The message's badge then shows only the channel (for example `sms`, with no status) until another non-verification event or a search runs load() again. With `-delivery-delay` negative, as the e2e harness runs it, no status event follows to repair it. The discovered note inbox-load-has-no-request-sequencing-for-the-messages-list-42f1fb.md says the verification map is guarded by newer(). That is true only for verifications present in both the map and the list. New ones are not covered.

### 6. README still says `/api/v1/wait`'s `otp` is the first 4-8 digit code in the body, but a Verify capture's `otp` is the verification code exactly as stored
severity: low
lens: api-contract
refuted_votes: 0/3
proven: none
disposition: followup F1.9

file: README.md:82

After F1.2, the `otp` field that `/api/v1/wait` (and `GET /api/v1/messages`) returns for a Twilio Verify capture is the verification code itself. It is not derived from the body, so it can be a 9-10 character or alphanumeric `CustomCode` such as `1234567890` or `AB1234`. README.md:82 still describes `otp` as "the first 4 to 8 digit code found in the body" for every `/api/v1/wait` response. That contradicts README.md:57 and the shipped behaviour, so the documented contract of `/api/v1/wait` is wrong for Verify captures.
