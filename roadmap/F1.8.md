# F1.8 — Should the local API refuse cross-site and rebound-host requests?

## Harm
A web page the developer opens while Caduceus runs can, by DNS rebinding to
127.0.0.1, read captured verification codes and SMS bodies, and can send
cross-site POSTs that approve or expire verifications. Steps on the default
branch: run Caduceus, visit a page that rebinds its hostname to 127.0.0.1:8026
and fetches `/api/v1/verifications` or `/2010-04-01/Accounts/x/Messages.json`.

## Spec
- **Surface:** `internal/server/server.go` (a guard on the local listener's
  branch of `ServeHTTP`, the `default:` case that hands off to `s.mux`, and a
  new `Options` field), a new `internal/server/guard.go` for the rule and its
  host-list parsing, `cmd/caduceus/main.go` (the new option), `README.md`
  (the Options table and a Docker Compose note), and the tests beside them.
- **Where it applies:** every request the local listener serves through
  `s.mux`: the UI, `/ca.pem`, `/api/v1/*`, and the Twilio Messaging and Verify
  routes served there for base-URL clients. CONNECT requests, tunnelled
  requests (`serveTunnelled`) and absolute-URL proxy requests
  (`serveProvider`) never reach the guard, so they are exempt without any
  carve-out of their own.
- **Interfaces:**
  - New option `-allowed-hosts` / `CADUCEUS_ALLOWED_HOSTS`: comma-separated
    host names added to the built-in list, e.g. `caduceus` or
    `caduceus,sms.test`. An entry may carry a port, which is ignored.
    `Options.AllowedHosts []string` carries it into the server.
  - **Host rule:** the request's `Host`, without its port, compared
    case-insensitively and with one trailing dot dropped, must be
    `localhost`, `127.0.0.1`, `::1` or an allowed name. Anything else,
    including an empty `Host`, is refused.
  - **Cross-site rule:** a request is refused when `Sec-Fetch-Site` is
    `cross-site` or `same-site`, or when it carries an `Origin` that is not
    `http://` + its own `Host` (`Origin: null` included). The one exception
    is a top-level `GET`/`HEAD` navigation (`Sec-Fetch-Mode: navigate`), so
    following a link to the inbox still opens it. Requests without these
    headers (curl, SDKs, test helpers) pass this rule.
  - **Refusal:** HTTP 403, logged once at info level with the host, origin,
    method and path. On `/2010-04-01/` and `/v2/` paths the body is Twilio's
    error shape via `twilioError` (code 20403), so a base-URL SDK surfaces the
    message. Everywhere else it is `writeError`'s `{"error": "…"}`. A Host
    refusal's message names the fix, e.g. `host "caduceus" is not allowed;
    add it with -allowed-hosts or CADUCEUS_ALLOWED_HOSTS`.
  - README: the new row in the Options table, and a short Docker Compose
    example showing `CADUCEUS_ALLOWED_HOSTS: caduceus` for app containers
    that call Caduceus by its service name.
- **Out of scope:** CORS headers or any cross-origin read access; an API
  token or other authentication; changing the default listen address or the
  Docker image's `CADUCEUS_LISTEN`; implicitly allowing the `-listen`
  address's own host (a LAN IP is added through `-allowed-hosts` like any
  other name); any change to proxy-mode behaviour.

## Acceptance
- (server unit test) with a request whose `Host` is `evil.example:8026`,
  each of `GET /api/v1/verifications`, `GET /api/v1/verifications/{sid}`,
  `GET /api/v1/events`, `GET /2010-04-01/Accounts/AC…/Messages.json` and
  `POST /api/v1/verifications/{sid}/expire` answers 403. No body contains
  the stored code or an SMS body, and the verification is still `pending`
  afterwards.
- (server unit test) with an allowed `Host`, `POST /api/v1/inbound`, `POST
  /api/v1/send` and `POST /v2/Services/{VA}/Verifications/{VE}`
  (`Status=approved`) carrying `Origin: http://evil.example` answer 403 and
  change nothing: no webhook is called, no message is stored, and the
  verification is unchanged. The same holds with `Sec-Fetch-Site:
  cross-site` and no `Origin`, and with `Origin: http://localhost:3000`
  (same site, other origin).
- (server unit test) a `GET /` with `Sec-Fetch-Site: cross-site` and
  `Sec-Fetch-Mode: navigate` answers 200. The same request as a `POST`
  answers 403.
- (server unit test) `Host` values `localhost:8026`, `127.0.0.1:8026`,
  `[::1]:8026` and `LOCALHOST.:8026` are accepted. `caduceus:8026` is refused
  by default and accepted when `AllowedHosts` holds `caduceus`, or
  `caduceus:9999` (port ignored). The refusal body names `-allowed-hosts` and
  `CADUCEUS_ALLOWED_HOSTS`.
- (server unit test) a refused `/2010-04-01/…` or `/v2/…` request answers
  Twilio's error shape with code 20403 and status 403. A refused `/api/v1/…`
  request answers `{"error": …}`.
- (server unit test) a tunnelled request for `api.twilio.com` or
  `verify.twilio.com`, and an absolute-URL proxy request, are served as
  before even though their `Host` is not in the allowed list.
- (e2e) the built binary, started with `CADUCEUS_ALLOWED_HOSTS=caduceus`,
  answers `GET /api/v1/messages` sent with `Host: caduceus` with 200. Started
  without it, the same request answers 403.
- (e2e) the existing suites pass unmodified: the stock twilio Node SDK
  through the proxy (Messaging and Verify) and the inbox UI browser fixture,
  whose page loads, list fetches, SSE stream and actions are same-origin.

## Notes
- From the F1 audit, record block 2 (`roadmap/audits/F1.md`); it also
  promotes the discovered note `local-rest-api-has-no-origin-or-host-check`
  (filed from F1.4). The exposure predates F1, which widened it with
  code-bearing routes (`/api/v1/verifications`, `verification` SSE events)
  and new write routes (`/api/v1/verifications/{sid}/expire`, Verify update
  and check). The provider routes are also served directly on the local
  listener (`internal/server/server.go`, the base-URL path), so the Messaging
  list `GET /2010-04-01/Accounts/{any}/Messages.json` is part of the same
  exposure; it returns every captured SMS body.
- Why it is a direction call and not a fix: a Host allowlist protects
  against DNS rebinding but breaks every client that reaches Caduceus by a
  name other than localhost — for example an app container calling
  `http://caduceus:8026/api/v1/wait` under docker compose. The README's
  Docker instructions only publish to 127.0.0.1 and do not mention compose,
  but nothing stops that setup. Which clients must keep working is a product
  decision. Requests arriving through the proxy carry the provider's Host by
  design and must stay exempt under any option; SDKs send no `Origin`, and
  base-URL clients send an allowed Host, so neither needs a route exemption.
- The audit did not test a real browser, so whether Chrome's or Firefox's
  private-network-access protections already block the rebinding read is
  open.

> **RECOMMENDATION (2026-10-26):** (b) — reject requests whose `Origin` (or
> `Sec-Fetch-Site: cross-site`) is not Caduceus's own origin, and check `Host`
> against localhost, 127.0.0.1 and [::1] plus names from a new
> `-allowed-hosts` / `CADUCEUS_ALLOWED_HOSTS` option, applied to every route
> on the local listener — the UI, `/api/v1/*` and the provider routes served
> there — and never to requests arriving through the proxy. It closes both
> the CSRF and the rebinding read, and gives Docker users an explicit
> one-line opt-in instead of a silent break.

> **ANSWER (2026-10-27):** b (default taken)
