# F1.1 — Verification store and lifecycle rules

Caduceus emulates Twilio Verify (milestone F1). This item is the storage and
the pure lifecycle rules underneath it; no HTTP route is added here.

## Spec
- **Surface:** `internal/store/store.go` (new `verifications` table in the
  same SQLite database, an idempotent migration for existing databases, new
  `Verification` type and methods, two new `Message` fields, email-aware
  recipient matching), `internal/store/store_test.go`; a new file for the
  lifecycle rules, e.g. `internal/store/verification.go`.
- **Interfaces:** (consumed by F1.2–F1.5 — keep these names)
  - `type Verification struct` with JSON-tagged fields `ID` (`VE` + 32 hex,
    via `NewSID("VE")`), `ServiceSID`, `AccountSID`, `To`, `Channel`, `Code`,
    `Status` (`pending | approved | canceled | max_attempts_reached | expired`),
    `SendAttempts []SendAttempt` (`SendAttempt{SID string; Channel string; Time time.Time}`,
    SID prefixed `VL`), `CheckAttempts int`, `CreatedAt`, `UpdatedAt`,
    `ExpiresAt time.Time` (JSON `expires_at`).
  - Lifecycle constants: `VerificationTTL = 10 * time.Minute`,
    `MaxSendAttempts = 5`, `MaxCheckAttempts = 5` (Twilio's defaults, fixed in
    F1).
  - `(*Store).AddVerification(v Verification) (Verification, error)`,
    `GetVerification(id string) (Verification, error)` (`ErrNotFound` when
    absent), `PendingVerification(serviceSID, to string) (Verification, error)`
    (the live pending one for that service and recipient, else `ErrNotFound`),
    `UpdateVerification(v Verification) (Verification, error)`,
    `ListVerifications(f Filter) ([]Verification, error)` (newest first,
    honours `Filter.To`).
  - Expiry: a verification is expired when `!now.Before(ExpiresAt)` and its
    status is `pending`. It is applied on read: such a verification is
    returned and stored as `expired`, and that write publishes an event like
    any other. The expiry write is conditional (`UPDATE … SET
    status='expired' WHERE id=? AND status='pending' AND expires_at <= ?`),
    never a whole-row write of a stale read, so it cannot overwrite a
    concurrent check's result or attempt count. `ExpiresAt` is set from `CreatedAt` and a resend does not move
    it.
  - `Message` gains `Channel string \`json:"channel,omitempty"\`` and
    `VerificationSID string \`json:"verification_sid,omitempty"\``.
  - `Event` gains `Verification *Verification \`json:"verification,omitempty"\``;
    every verification write publishes `Event{Type: "verification"}`.
  - `Clear()` also deletes every verification; pruning keeps at most `max`
    verifications, oldest dropped first, like messages.
  - Recipients: an address containing `@` is stored lowercased with an empty
    `recipient_digits`, and a `Filter.To` containing `@` matches it
    case-insensitively as a whole address; a phone `Filter.To` matches by
    digits as today and never matches an email recipient. Applies to `List`,
    `ListVerifications`, `Filter.Matches` and `PendingVerification`.
  - Migration: `Open` on a database created before F1 adds the new
    `messages` columns (idempotent `ALTER TABLE … ADD COLUMN`, defaulting to
    `''`), normalises existing email recipients to the new rule (lowercased
    `recipient`, empty `recipient_digits` for every row containing `@`), and
    creates the `verifications` table; reopening a migrated database is a
    no-op.
  - `-max-messages` now also caps verifications; the README options table
    says so.
- **Out of scope:** HTTP routes and Twilio JSON rendering (F1.2, F1.3),
  serialising concurrent Verify requests (the server does that, F1.2/F1.3),
  the Caduceus REST API for verifications (F1.4), UI (F1.5), configurable TTL
  or limits (F1 decided on Twilio's fixed defaults).

## Acceptance
- (store unit test) A verification added, then fetched by `GetVerification`
  and by `PendingVerification(service, to)`, round-trips every field,
  including `SendAttempts` and `ExpiresAt`, across a close/reopen of a
  persistent database.
- (README) the `-max-messages` row says it also caps verifications.
- (store unit test) `PendingVerification` returns `ErrNotFound` for a
  different service SID, and for the same recipient once the verification is
  `approved`, `canceled` or `max_attempts_reached`.
- (store unit test) A pending verification whose `ExpiresAt` equals or
  precedes now is reported as `expired` by `GetVerification` and
  `ListVerifications`, a subscriber receives a `verification` event for that
  transition, an already-`approved` verification past its `ExpiresAt` stays
  `approved`, and `PendingVerification` no longer returns it. Tests set
  `ExpiresAt` directly; none sleeps.
- (store unit test) `Clear()` empties verifications as well as messages, and
  pruning beyond `max` drops the oldest verification.
- (store unit test) Every verification write delivers a `verification` event
  to a subscriber, carrying the updated verification.
- (store unit test) `List(Filter{To: "Ada@Example.com"})` returns a message
  sent to `ada@example.com` and not one sent to `ada1@example.com`;
  `List(Filter{To: "1"})` does not return the message sent to `ada1@example.com`;
  digit matching for phone numbers is unchanged (the existing
  `TestListFilters` still passes unmodified).
- (store unit test) A message stored with `Channel` and `VerificationSID`
  returns both fields from `Get` and `List`.
- (store unit test) A database file created with the pre-F1 schema (the
  `schema` constant as it is on main before this item) opens, accepts a new
  message with `Channel` set, and still returns its old messages; an old row
  sent to `Ada1@Example.com` is then matched by `Filter{To:
  "ada1@example.com"}` and not by `Filter{To: "1"}`; opening it a second
  time succeeds.
- (store unit test) `PendingVerification(service, "Ada@Example.com")` finds
  a verification stored to `ada@example.com`.
