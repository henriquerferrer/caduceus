# F1.4 — Verifications in the Caduceus REST API, with an expire hook

Tests need to see a verification's state and reach the expired path without
waiting Twilio's 10 minutes. Decided at the F1 brainstorm: a read endpoint, an
expire hook, and the existing reset clears verifications too.

## Spec
- **Surface:** `internal/server/server.go` (new handlers and routes; `/api/v1/wait`
  `to` validation), `internal/server/server_test.go`, `README.md` (endpoint
  table).
- **Interfaces:**
  - `GET /api/v1/verifications?to=` returns `{"verifications": [...]}`,
    newest first: the store's `Verification` JSON (from F1.1), including
    `code`, `status`, `send_attempts`, `check_attempts` and `expires_at`.
  - `GET /api/v1/verifications/{sid}` returns one, 404 `{"error": …}` when
    absent.
  - `POST /api/v1/verifications/{sid}/expire` sets a pending verification's
    `ExpiresAt` to now, so it reads as `expired`; returns the verification;
    404 when absent; 409 `{"error": …}` when it is not `pending`. It takes
    F1.2's `verifyMu`, so a concurrent check cannot overwrite it.
  - `DELETE /api/v1/messages` clears verifications as well (F1.1's `Clear`), holding
    `verifyMu` so a reset never interleaves with a Verify send or check.
  - `GET /api/v1/wait?to=` accepts an email address (contains `@`) as well as
    a phone number; anything with neither digits nor `@` is still rejected
    with 400.
- **Out of scope:** the Twilio-shaped endpoints (F1.2, F1.3; this item
  depends on F1.2 only for its `verifyMu`), UI (F1.5), any
  way to create or approve a verification through the Caduceus API (the app
  does that through Twilio's API), a separate verifications reset endpoint.

## Acceptance
- (server test) after two verifications are stored, `GET
  /api/v1/verifications` returns both newest first with `code`, `status` and
  `expires_at`; `?to=` filters to one recipient.
- (server test) `GET /api/v1/verifications/{sid}` returns it; an unknown sid
  returns 404.
- (server test) `POST /api/v1/verifications/{sid}/expire` on a pending one
  returns it with `status: expired`; a second call returns 409; an unknown
  sid returns 404.
- (server test) `DELETE /api/v1/messages` leaves `GET /api/v1/verifications`
  empty.
- (server test) `GET /api/v1/wait?to=ada@example.com` returns a message
  stored to `Ada@Example.com`; `?to=nobody` still returns 400.
- (README) the endpoint table lists the three new routes and notes that
  `DELETE /api/v1/messages` also clears verifications.

## Notes
- Premises checked against main at c2659de. `DELETE /api/v1/messages`
  already deleted verifications (`store.Clear`, F1.1) and already held
  `verifyMu` (`handleClear`, F1.2). That clause needed no code; the new
  `TestClearDeletesVerifications` pins it through the new list route. `handleWait` rejected any `to` without digits, as the two
  F1.1 discovered notes on it say; it now accepts an address with `@`.
- The store's `Verification` JSON carries `code`, `status`,
  `send_attempts`, `check_attempts` and `expires_at`, as the item says.
- Choices the item left open: the 404 body is
  `{"error": "verification not found"}`; the 409 body names the current
  status. `?to=` with neither digits nor `@` does not filter, as on
  `GET /api/v1/messages`. The list and get routes do not take `verifyMu`:
  the store applies expiry with a conditional write.
