# F1.11 — The local-listener guard accepts an https origin for the same host

Behind an HTTPS reverse proxy whose name is allowed, the browser sends
`Origin: https://<host>`. The guard accepts only `http://` + Host, so the inbox
loads but its writes (clear, expire, simulate inbound) answer 403. An Origin
of `https://` + exactly the request's Host can only come from a page served
from that host, so accepting it is as safe as the `http://` form.

## Spec
- **Surface:** `internal/server/guard.go`, `internal/server/guard_test.go`,
  `README.md`.
- **Interfaces:** the Origin rule becomes: accepted when it is `http://` or
  `https://` followed by exactly the request's Host (same host and same port,
  or both without a port). Every other rule of F1.8 is unchanged: the Host
  allow-list, the Sec-Fetch-Site rule and the top-level navigation exemption.
- **Out of scope:** trusting `X-Forwarded-Host`; terminating TLS in Caduceus itself; any change to proxied
  requests (the plain-HTTP proxy decision stays as F1.8 made it).

## Acceptance
- (server test) with Host `sms.test` allowed, a POST to a write endpoint with
  `Origin: https://sms.test` is answered (not 403).
- (server test) refused with 403: `Origin: https://evil.test`,
  `Origin: https://sms.test:8443` with Host `sms.test`, `Origin: https://sms.test`
  with Host `other.test` (not allowed), and `Origin: null`.
- (server test) the existing `http://` + Host cases still pass unchanged.
- (README) the guard paragraph says Caduceus can sit behind an HTTPS reverse
  proxy whose host name is in `-allowed-hosts`, and that the proxy must
  forward the original Host (nginx: `proxy_set_header Host $http_host`, which
  keeps the port; nginx's default sends the upstream's name, and `$host`
  drops the port). `X-Forwarded-Host` is not trusted.
