# F1.6 — Stock twilio Node SDK drives Verify through the proxy (e2e)

The zero-code invariant is proven, not claimed: the official twilio Node SDK,
unmodified and configured only by `HTTP_PROXY`/`HTTPS_PROXY` and
`NODE_EXTRA_CA_CERTS`, starts and checks a verification against the built
binary.

## Spec
- **Surface:** `e2e/e2e_test.go`, a new script beside `e2e/twilio-node/send.mjs`
  (e.g. `e2e/twilio-node/verify.mjs`), no change to `e2e/twilio-node/package.json`
  dependencies.
- **Interfaces:** the script takes subcommands the Go test invokes in turn —
  `start TO` calls
  `client.verify.v2.services(SID).verifications.create({to, channel: "sms"})`,
  `check TO CODE` calls
  `client.verify.v2.services(SID).verificationChecks.create({to, code})` —
  with a made-up `VA…` SID and fake credentials, and prints the SDK object's
  `sid`, `status`, `valid` and `dateCreated` (as ISO) as JSON, or the
  `RestException`'s `status` and `code` on error, so the Go test can assert
  them. The Go test reads the code from `/api/v1/wait` between the calls.
- **Out of scope:** other SDKs or languages (milestone F4), channels other
  than sms in e2e (covered at the server-test layer in F1.2), the UI (F1.5),
  the Caduceus verifications API (F1.4).

## Acceptance
- (e2e, `just e2e`) `start` through the SDK returns a `VE…` sid with status
  `pending` and a valid `dateCreated`; `/api/v1/wait` returns that
  verification's code; `check` with a wrong code returns `pending`/`valid:
  false` through the SDK; `check` with the right code returns
  `approved`/`valid: true`.
- (e2e) a `check` after approval makes the SDK throw a `RestException` with
  code 20404, so the SDK parses the emulated error shape.
- (e2e) a second `start` to the same number before checking returns the
  same sid.
- (e2e) the test fails, not skips, in CI when the node fixture is missing,
  as `TestTwilioNodeSDK` already does.
