# F1.7 — A Verify write never overwrites a stored expiry

F1 audit, record block 1 (`roadmap/audits/F1.md`), proven in a sandbox: the
Verify handlers hold `verifyMu`, read a verification, and write the whole row
back with `UPDATE … WHERE id = ?`. The REST reads (`GET /api/v1/verifications`
and `GET /api/v1/verifications/{sid}`) store an expiry without taking
`verifyMu`. When the TTL ends between a handler's read and its write, the
expiry is stored and published, then the handler's stale write replaces it
with `approved` or `pending`. This fails F1.2's spec, which says every Verify
read-modify-write is serialised by `verifyMu`.

## Harm
An app under test, or the developer watching the inbox, can be told a
verification is `approved` after Caduceus had already stored and published it
as `expired`. Production Twilio would answer 20404 there. Steps on the
default branch: start a verification, then check the right code at the
moment its TTL ends while the inbox UI (which calls `GET
/api/v1/verifications` on every SSE event) is open.

## Spec
- **Surface:** `internal/store/verification.go` (`updateVerification`, and
  `SendVerification` where it updates), `internal/server/verify.go` (the
  start, update and check handlers' write paths), `internal/server/server.go`
  (`handleListVerifications`, `handleGetVerification`), and the tests beside
  them.
- **Interfaces:** a handler's write of a verification is conditional on the
  status it read: the store's update matches `WHERE id = ? AND status = ?`
  with the status the handler read. A write whose condition matches no row
  fails with a sentinel error (e.g. `store.ErrStale`). The handler then
  re-reads under `verifyMu` and answers from the current state: `20404`
  (HTTP 404) for check, fetch and update, and a new verification for a send.
  Taking `verifyMu` in the two REST reads as well is allowed, but it is not
  enough on its own: the store's expiry-on-read runs on every read path.
- **Out of scope:** the UI badge's own request sequencing (parked as record
  block 3); configurable TTL; any change to Twilio response shapes.

## Acceptance
- (server test, with the store clock injected and the handler paused between
  its read and its write, as the audit's sandboxed experiment did) for each
  of: check with the right code, check with a wrong code, update to
  `approved`, and resend on start, a `GET /api/v1/verifications/{sid}` in
  that window stores `expired`, and afterwards the verification is still
  `expired`. The published `verification` events for that sid end at
  `expired`, with no later `approved` or `pending` event.
- (server test) the check in that window answers 404 code 20404, never 200
  `approved`.
- (store unit test) an update conditioned on `pending` against a row
  already `expired` returns the sentinel error and leaves the row unchanged.
- (server test, `-race`) the existing Verify concurrency tests still pass
  unmodified.
