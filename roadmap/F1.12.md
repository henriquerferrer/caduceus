# F1.12 — The inbox keeps a verification its SSE event delivered when an older list lands

F1 audit finding `### 3` (`roadmap/audits/F1.md`, with its Playwright proof):
`load()` in the inbox replaces the whole `verifications` map with the list it
fetched, so a verification added by an SSE `verification` event after that list
was read is dropped when the older list lands last. The badge then shows only
the channel (`sms`, no status) until something reloads.

## Spec
- **Surface:** `internal/server/ui/index.html` (`load()`, the `verifications`
  map), `e2e/ui/inbox.spec.mjs`.
- **Interfaces:** `load()` merges the fetched list into the map instead of
  replacing it, deciding by order on the client, never by comparing the
  server's timestamps with the browser's clock (behind F1.11's reverse proxy
  they can be different machines). A counter records each `load()` start and
  each SSE `verification` arrival; a verification the list does not contain
  is kept when its SSE event arrived after that load started. The existing
  `newer()` guard still decides between two copies of the same verification.
  A `clear` event still empties the map.
- **Out of scope:** request sequencing for the messages list (a separate,
  already-triaged note); any visual change to the badge.

## Acceptance
- (browser, `e2e/ui`) the audit's scenario as a regression test: with a load
  started before a Verify send and its verification list held until after the
  SSE event, the badge still reads `sms · pending` 3 seconds after the stale
  list lands, run with `-delivery-delay` negative.
- (browser) after `DELETE /api/v1/messages`, no badge or verification remains.
- (browser) the existing inbox specs still pass, including the axe scan.
