# F1.5 — Verification badge in the inbox UI, gated by a browser fixture

A message produced by a Verify send shows its channel and the verification's
live status, so a developer watching the inbox sees "sms · pending" turn into
"approved" or "expired" as the app works. Decided at the F1 reconcile: the
badge is gated in CI by a Playwright + axe fixture that `just e2e` runs; the
repo has no browser harness yet, and this item adds it.

## Spec
- **Surface:** `internal/server/ui/index.html` (the single embedded page; its
  existing render loop and SSE subscription); a new browser fixture
  `e2e/ui/` (its own `package.json` and lockfile with `@playwright/test` and
  `@axe-core/playwright`, like `e2e/twilio-node/`) with the Go e2e test or
  script that starts the built binary for it; the `justfile` `e2e` recipe
  (install the fixture and its Chromium on first run, then run it).
- **Interfaces:** consumes the message's `channel` and `verification_sid`
  fields (F1.1), `GET /api/v1/verifications` (F1.4) for each verification's
  initial status and `expires_at`, and the `verification` SSE event on
  `/api/v1/events` (F1.1) for live updates. The badge shows `expired` once
  `expires_at` has passed even if no event arrives. No new endpoint. CI
  reaches the fixture through `just e2e` alone; if running it in CI proves to
  need a `.github/` change, that PR is a human's to merge — escalate, do not
  route around it.
- **Out of scope:** any other UI change; a separate verifications screen; a
  UI control to expire, approve or cancel (tests use the API); a design
  system or surface contract (this milestone changes one element of one
  page); browser coverage of screens other than the inbox.

## Acceptance
- (browser, the new Playwright fixture run by `just e2e`) after a Verify
  send through the emulated endpoint, the message row shows the channel and
  `pending`; after a correct check it shows `approved` without a page
  reload; after `POST /api/v1/verifications/{sid}/expire` on another
  verification it shows `expired` without a reload.
- (browser) a message with no `verification_sid` renders with no badge.
- (browser) an `@axe-core/playwright` scan of the inbox with a badge visible
  reports no serious or critical violations, and the status is conveyed as
  text, not by colour alone.
- (e2e) in CI (`CI` set) the fixture fails, not skips, when its
  dependencies are missing, as `TestTwilioNodeSDK` does.
- (ui-design hard gates) pass, per the item's `ui` review dimension.

## Notes
- Premises checked against main at 2b30579; none was stale. The page is
  the single embedded `internal/server/ui/index.html`, with its render loop
  and an `/api/v1/events` subscription that reloaded on every event.
  `Message` carries `channel` and `verification_sid` (omitted when empty).
  `GET /api/v1/verifications` returns `status` and `expires_at`. The store
  publishes `{"type": "verification", "verification": {...}}`.
  `POST /api/v1/verifications/{sid}/expire` exists. `TestTwilioNodeSDK`
  fails with `CI` set and skips without it. The CI e2e job runs `just e2e`
  on `vars.RUNNER_LABEL || 'ubuntu-24.04'`, and `gh variable list` shows no
  repository variables, so the fixture reaches CI through the recipe and no
  `.github/` change was needed.
- The axe scan found serious `color-contrast` violations that predate this
  item: `--muted` text on the outbound bubble was 4.05:1 in both themes.
  The acceptance asks for a clean scan of the inbox, so `--muted` moved to
  `#69675f` (light) and `#a6a49d` (dark). That token is the only style change
  outside the badge.
- Choices the item left open: the badge reads `<channel> · <status>` with
  the API's status value; a message whose verification the page does not
  have shows the channel alone; the page clock decides expiry, repainting
  the badges in place at the soonest pending `expires_at` in the open thread; between a list
  read and an event, the later `updated_at` wins.
- ui-design: no design system or surface contract exists, so the token lint
  and contract checks are not active. Mobbin was not queried: this adds one
  element to an existing screen, which is neither a net-new screen nor a
  redesign. Screenshots were taken in light and dark, at 1100px and 390px.
