# F1.9 — Test the verification event and Twilio's documented Verify limits

Two confirmed F1 audit findings (`roadmap/audits/F1.md`) are missing tests on
behaviour that works today. The other two findings this item used to park
moved out at the F2 brainstorm: `### 3` (the badge race) is F1.12, and `### 6`
(README otp wording) is a line of F1.10.

## Spec
- **Surface:** `internal/store/store_test.go`, `internal/server/server_test.go`.
  No product code changes; if a test exposes a defect, fix it in this item.
- **Interfaces:** none new. The tests use `Store.Subscribe` and the existing
  server test helpers (`startVerification`, `checkVerification`).
- **Out of scope:** the badge race (F1.12), README wording (F1.10), code-length
  validation (F1.10).

## Acceptance
- (store test) `SendVerification` delivers exactly one `verification` event
  carrying the new verification (sid, status `pending`) to a subscriber, and a
  resend to the same pending verification delivers one more. Removing the
  `publishVerification` call from `SendVerification` makes this test fail
  (audit finding `### 4`).
- (server test) the check-attempt limit and the pending lifetime are asserted
  against literals taken from Twilio's documentation, not the code's constants:
  the 6th check of a wrong code answers 60202 (HTTP 429), and a verification
  read 10 minutes after it was created, through an injected store clock, is
  `expired`. Each literal carries a comment with the Twilio docs URL it comes
  from (audit finding `### 5`).
