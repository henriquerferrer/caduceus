# F1.2 — Intercept verify.twilio.com and emulate starting a verification

An app using Twilio Verify, unmodified, gets its codes in the Caduceus inbox
instead of on a real phone. Decided at the F1 brainstorm: emulate
Verifications + VerificationCheck only (checking is F1.3); accept any `VA…`
service SID with no setup (the app's existing service SID works); capture
every channel, tagged; random 6-digit code or the request's `CustomCode`;
Twilio's full lifecycle with its default limits.

## Spec
- **Surface:** `internal/server/proxy.go` (`intercepted`), `internal/server/server.go`
  (host-aware provider routing for tunnelled and plain-HTTP absolute-form
  requests), a new `internal/server/verify.go` (routes, handlers, Twilio JSON
  rendering), `internal/server/twilio.go` (`twilioError` gains an HTTP status
  argument; Messages list/fetch exclude Verify captures),
  `internal/server/server_test.go`, `README.md`.
- **Interfaces:**
  - Routes, registered on the local mux (base-URL clients) and on the proxy's
    provider table: `POST /v2/Services/{service}/Verifications` (form `To`,
    `Channel` required; `CustomCode` optional),
    `GET /v2/Services/{service}/Verifications/{sid}`,
    `POST /v2/Services/{service}/Verifications/{sid}` (form `Status` =
    `canceled` or `approved`). F1.3 adds `VerificationCheck` beside them.
  - `intercepted(host)` is true for `api.*.twilio.com` (unchanged) and for
    `verify.twilio.com` plus its regional forms (`verify.*.twilio.com`); every
    other host stays false. The existing `TestInterceptsOnlyTheMessagingHost`
    table row `"verify.twilio.com": false` encodes the rule this item
    deliberately changes: flip that row and rename the test to match the new
    rule. This is a spec change, decided at the F1 brainstorm; every other
    row stays as it is.
  - Proxy routing is host-aware, for HTTPS-tunnelled requests and for
    plain-HTTP absolute-form requests to an intercepted host alike: Verify
    routes answer only on a `verify.*` host and Messaging routes only on an
    `api.*` host. Any other path on an intercepted host, including a Verify
    path sent to `api.twilio.com`, passes through to the real provider
    untouched, and an absolute-form request never reaches the Caduceus API or
    UI routes.
  - A send captures one outbound message via the existing `capture` path with
    `Provider: "twilio-verify"`, `Channel` = the request's channel,
    `VerificationSID` = the verification's sid, `From: "Verify"`, and body
    `Your verification code is: ` followed by the code. The message's `OTP`
    is set from the verification's code verbatim (`capture` takes a preset
    OTP instead of re-deriving it from the body), so `otp` always equals the
    code, including a 9–10 character or alphanumeric `CustomCode`. For phone
    channels `/api/v1/wait` reads it unchanged; for `email`, `wait` needs
    F1.4.
  - Channels accepted: `sms`, `call`, `email`, `whatsapp`, `sna` (the SDK's
    `VerificationChannel` enum) plus `auto` (captured and tagged `auto`, as
    decided at the brainstorm; the SDK types `channel` as a string, so it
    can send it). Confirm the set against Twilio's docs and record the URL.
  - Service scoping: a verification belongs to the `{service}` it was
    started on. Fetch, update and check-by-`VerificationSid` on a different
    service segment return `20404` (HTTP 404), as Twilio does; the service
    SID is the emulation's only tenant boundary, so this is never relaxed.
  - Messages API fidelity: `GET …/Messages.json` and `GET …/Messages/{sid}`
    on the Twilio Messaging emulation exclude `twilio-verify` captures and
    are otherwise unchanged: Messaging captures and simulated inbound
    messages (provider `simulated`) are still listed and fetchable.
  - `account_sid` is the Basic-auth username when it starts with `AC`, else
    the fixed placeholder `AC00000000000000000000000000000000`.
  - Validation: missing `To` or `Channel`, an unknown channel, a phone
    channel whose `To` is not E.164 (`+` then digits), or an `email` channel
    whose `To` has no `@`, returns `60200` (HTTP 400). A service segment not
    starting with `VA` returns `20404` (HTTP 404). Other Verify parameters
    (`Locale`, `CustomMessage`, `CustomFriendlyName`, `TemplateSid`,
    `AppHash`, `Amount`, `Payee`, `RiskCheck`, `DeviceIp` and the rest) are
    accepted and ignored.
  - Resource JSON matches Twilio's Verification shape (snake_case fields the
    stock SDK reads: `sid`, `service_sid`, `account_sid`, `to`, `channel`,
    `status`, `valid`, `lookup`, `amount`, `payee`, `send_code_attempts`
    entries shaped `{attempt_sid, channel, time}`, `date_created`,
    `date_updated`, `sna`, `url`). Dates are ISO 8601 UTC
    (`2006-01-02T15:04:05Z`): the SDK parses Verify dates with
    `iso8601DateTime`, unlike Messaging's RFC 2822, so reusing the Messaging
    renderer would hand the SDK invalid dates. `sna` is null except on the
    `sna` channel, where it is `{"url": …}` with a Caduceus-local URL that is
    never fetched (the shape the SDK reads; the SNA flow itself is not
    emulated). Twilio errors use Twilio's JSON error shape and its HTTP
    statuses.
  - Lifecycle on send (confirm each against Twilio's Verify docs and record
    the doc URLs under `## Notes`; where the docs differ from this spec,
    follow the docs and record the difference): a send to a recipient with a
    live pending verification on the same service reuses it (same sid, same
    code, `ExpiresAt` unchanged, `channel` updated to the new channel, a new
    `CustomCode` ignored, one more `send_code_attempts` entry); the send that
    would exceed `MaxSendAttempts` is refused with `60203` (HTTP 429).
    Updating a pending verification with `Status=canceled` or `approved`
    sets that status; updating one that is not pending returns `20404`
    (HTTP 404).
  - Concurrency: Verify mutations are serialised in the server by one mutex
    (`verifyMu`) around find-or-create and every read-modify-write, so
    parallel sends to one recipient never create two pending verifications.
    Every later Verify writer (F1.3's check, F1.4's expire hook) takes the
    same mutex.
  - Twilio docs: where this item says to confirm against Twilio's docs,
    read them; if they cannot be read in this run, set the item
    `status: blocked` with the question rather than record a URL never
    read or guess the behaviour.
- **Out of scope:** VerificationCheck and the check-attempt limit (F1.3);
  Services, Rate Limits, Messaging Configurations, Webhooks, Access Tokens,
  TOTP Entities/Factors/Challenges (all pass through); SNA's real URL flow
  (an `sna` send captures a code like any channel); per-service code length,
  friendly name or templates (Services are not emulated, so the default
  6-digit code and generic body are used); the Caduceus REST API for
  verifications (F1.4); UI (F1.5); the stock-SDK e2e (F1.6); configurable
  TTL or limits.

## Acceptance
- (server unit test, table-driven) `intercepted` is true for
  `api.twilio.com`, `api.dublin.ie1.twilio.com`, `verify.twilio.com`,
  `verify.dublin.ie1.twilio.com`, and false for `lookups.twilio.com`,
  `verify.twilio.com.evil.test`, `example.com`.
- (server test, through the HTTPS proxy with a fake upstream as in
  `TestProxyPassesUnemulatedEndpointsUpstream`) `GET
  https://verify.twilio.com/v2/Services/VAx` reaches the upstream with the
  caller's credentials and nothing is captured; `POST
  https://api.twilio.com/v2/Services/VAx/Verifications` also reaches the
  upstream rather than the emulation.
- (server test) a plain-HTTP absolute-form `GET
  http://verify.twilio.com/api/v1/messages` sent to the proxy is not
  answered by the Caduceus API. The test stubs `srv.direct` (the transport
  `forward` uses), never reaching the network.
- (server test, through the proxy) `POST
  https://verify.twilio.com/v2/Services/VAx/Verifications` with
  `To=+15550003333&Channel=sms` returns 201 with a `VE…` sid,
  `status: pending`, `valid: false`, one `send_code_attempts` entry, and an
  ISO 8601 `date_created`; `/api/v1/wait?to=+15550003333` returns a message
  whose `otp` is a 6-digit code, whose `channel` is `sms` and whose
  `verification_sid` is that sid.
- (server test) `CustomCode=4321` makes the captured message's `otp` 4321;
  `CustomCode=1234567890` makes it `1234567890`; `CustomCode=AB1234` makes it
  `AB1234`.
- (server test) a verification started on `VAone` returns 404 code 20404
  on fetch and on update through `/v2/Services/VAother/...`, and is
  unchanged afterwards.
- (server test) `Channel=email` to `ada@example.com` and `Channel=call`
  each capture a message tagged with that channel; `Channel=email` with
  `To=+15550003333` returns 400 code 60200.
- (server test) a second send to the same recipient on `whatsapp` returns
  the same sid and code with two `send_code_attempts` and `channel:
  whatsapp`; the send after the fifth returns 429 code 60203.
- (server test) 10 parallel sends to one new recipient: exactly 5 return
  201, all with one sid, and 5 return 429 code 60203; the store holds
  exactly one verification for it, with exactly 5 `send_attempts` (no
  attempt lost to a concurrent append).
- (server test) `GET …/Verifications/{sid}` returns the verification;
  `POST …/Verifications/{sid}` with `Status=canceled` returns `canceled`; an
  unknown sid returns 404 code 20404; missing `To` or `Channel` returns 400
  code 60200; a service segment `XYz` returns 404 code 20404.
- (server test) Basic-auth user `ACabc` yields `account_sid: ACabc`; user
  `SKkey` yields the placeholder.
- (server test) after a Verify send, `GET
  /2010-04-01/Accounts/ACx/Messages.json` lists none of its messages, and
  fetching the captured message's sid there returns 404; a simulated inbound
  message from `POST /api/v1/inbound` is still listed there and fetchable by
  its sid.
- (server test) updating a canceled verification returns 404 code 20404.
- (server test) the same routes answer on the local base URL
  (`http://127.0.0.1:port/v2/Services/…`) without the proxy.
- (README) the paragraph saying Verify codes go to real phones is replaced
  by how Verify is emulated: endpoints, any service SID, all channels
  captured, Twilio's limits, the parameters accepted and ignored, and what
  still passes through.

## Notes
- Between F1.2 and F1.3 merging, `verify.twilio.com` is intercepted while
  `VerificationCheck` still passes through to real Twilio (which answers
  20404 for an emulated `VE…` sid). There is no release in between; F1.3
  is next on the frontier (it depends only on F1.2), so ship them back to
  back.
- Twilio docs read for this item (2026-10-26):
  - https://www.twilio.com/docs/verify/api/verification — the `Channel`
    request parameter accepts `email`, `sms`, `whatsapp`, `call`, `sna` or
    `auto`, the set implemented (the response property also mentions `rcs`,
    which is not accepted here). Update accepts only `canceled` or
    `approved`. The examples render dates as ISO 8601 although the property
    text says RFC 2822; the SDK parses them with `iso8601DateTime`
    (e2e/twilio-node/node_modules/twilio/lib/rest/verify/v2/service/verification.js),
    so ISO 8601 is used. `lookup` is `{}` in the non-SNA examples, as
    rendered here. The examples' `send_code_attempts[].channel` is `SMS` in
    some and lowercase in others; it is rendered lowercase, as sent. The
    page says `CustomCode` is 4 to 10 characters; this item does not
    validate its length (filed as a discovered note).
  - https://www.twilio.com/docs/api/errors/60203 — HTTP 429, raised after
    more than 5 send attempts without completing the lifecycle; matches.
  - https://www.twilio.com/docs/api/errors/60200 — HTTP 400, message
    `Invalid parameter: To`; used with the parameter's name.
  - https://www.twilio.com/docs/verify/developer-best-practices — "If your
    users make another request within the 10 minutes, they will receive the
    same token"; matches the reuse rule. The docs are silent on the channel
    update and on ignoring a new `CustomCode` on reuse; implemented as this
    spec says.
  - https://www.twilio.com/docs/verify/api/verification-check — Twilio
    deletes a verification once approved, expired or out of check attempts,
    and VerificationCheck then returns 404. The Fetch section of the
    Verification page says nothing about fetching such a verification, so
    fetch here returns it with its status, as this spec says; updating one
    that is not pending returns 20404, as this spec says (the docs do not
    say either way).
- Premises checked against main at 9d0a016: `intercepted`,
  `TestInterceptsOnlyTheMessagingHost` (with its `"verify.twilio.com":
  false` row), `TestProxyPassesUnemulatedEndpointsUpstream`, `srv.direct`
  as `forward`'s transport, `capture` re-deriving the OTP, `twilioError`
  without a status argument, and the README paragraph all matched. The test
  is renamed `TestInterceptsOnlyTheMessagingAndVerifyHosts`; its other rows
  are kept and `verify.dublin.ie1.twilio.com` / `verify.twilio.com.evil.test`
  added.
- Found while writing the RED test: before this item a plain-HTTP
  absolute-form `GET http://api.twilio.com/api/v1/messages` was answered by
  the Caduceus API. Fixed here: absolute-form requests are served only by
  their host's provider routes, and anything else is forwarded.
- Choices the spec leaves open: an update `Status` other than `canceled` or
  `approved` returns 60200; the resource `url` uses the request's scheme and
  host; the `sna.url` is `http://<the local address the request arrived
  on>/sna/<sid>`; fetch also takes `verifyMu`, because a read can store an
  expiry.
- Review fixes: a send stores its verification and the message carrying
  the code in one transaction (`store.SendVerification`), so a send whose
  message cannot be stored uses up no attempt. Verify storage failures
  answer Twilio's `20500` (HTTP 500,
  https://www.twilio.com/docs/api/errors/20500, read 2026-10-26). The inbox
  clear (`DELETE /api/v1/messages`) deletes verifications, so it also takes
  `verifyMu`.
