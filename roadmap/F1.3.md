# F1.3 — Emulate checking a verification, with Twilio's attempt limit

The other half of Verify: the app submits the code the user typed and gets
Twilio's answer, including the error paths production would give it.

## Spec
- **Surface:** `internal/server/verify.go` (the check route and handler,
  beside F1.2's, and F1.2's fetch handler, which this item makes return
  `20404` for a verification that is no longer pending), `internal/server/server_test.go`, `README.md` (the Verify
  section F1.2 wrote).
- **Interfaces:**
  - Route, on the local mux and the proxy's `verify.*` provider table:
    `POST /v2/Services/{service}/VerificationCheck` (form `Code` plus `To` or
    `VerificationSid`; neither, or a missing `Code`, returns `60200`, HTTP
    400).
  - Response JSON matches Twilio's VerificationCheck shape: `sid` (the
    verification's `VE…` sid), `service_sid`, `account_sid`, `to`,
    `channel`, `status`, `valid`, `amount`, `payee`, `date_created`,
    `date_updated` (ISO 8601 UTC, as in F1.2), `sna_attempts_error_codes`.
  - Lifecycle (confirm each against Twilio's Verify docs, including the exact
    check on which `60202` fires, and record the doc URLs under `## Notes`;
    where the docs differ from this spec, follow the docs, adjust the
    matching acceptance line to the documented behaviour, and record why):
    a wrong code returns 200 with `status: pending`, `valid: false` and
    counts one check attempt; the right code returns 200 `approved`,
    `valid: true`; exceeding `MaxCheckAttempts` returns `60202` (HTTP 429)
    and leaves the verification `max_attempts_reached`. A check or a fetch
    with no live pending verification (unknown, approved, canceled, expired,
    max attempts reached) returns `20404` (HTTP 404).
  - Service scoping: a check by `VerificationSid` for a verification started
    on another service, or by `To` where the only pending verification is on
    another service, returns `20404` (HTTP 404) and counts no attempt.
  - Concurrency: checks share F1.2's Verify mutex, so parallel checks never
    exceed the attempt limit.
  - Twilio docs: where this item says to confirm against Twilio's docs,
    read them; if they cannot be read in this run, set the item
    `status: blocked` with the question rather than record a URL never
    read or guess the behaviour.
- **Out of scope:** the send side (F1.2); the Caduceus REST API and expire
  hook (F1.4); UI (F1.5); configurable limits.

## Acceptance
- (server test, through the proxy) after a send, a wrong code returns 200
  `pending`/`valid: false`; the right code returns 200 `approved`/`valid:
  true` with the verification's `VE…` sid; a further check returns 404 code
  20404, and so does a fetch of the verification.
- (server test) checking by `VerificationSid` instead of `To` behaves the
  same; a check with neither, or with no `Code`, returns 400 code 60200.
- (server test) repeated wrong checks reach 429 code 60202 at the
  documented attempt, after which the verification is
  `max_attempts_reached` and a further check or fetch returns 404 code
  20404.
- (server test) after `POST …/Verifications/{sid}` with `Status=canceled`, a
  check returns 404 code 20404.
- (server test) a verification started on `VAone`, checked with its right
  code through `/v2/Services/VAother/VerificationCheck` by `VerificationSid`
  and by `To`, returns 404 code 20404 both times and stays `pending` with
  no check attempt recorded.
- (server test) a verification stored with `ExpiresAt` in the past (set
  through the store, no sleeping) answers a check with 404 code 20404.
- (server test) 10 parallel wrong checks against one verification record no
  more than `MaxCheckAttempts` attempts.
- (server test) the check route answers on the local base URL without the
  proxy, and a check sent to `api.twilio.com` passes through upstream.
- (README) the Verify section documents checking and its error codes.

## Notes
- Premises checked against main at 254081d: `internal/server/verify.go`
  holds F1.2's start, fetch and update handlers and `verifyMu`; F1.2's fetch
  answered 200 for a verification that was not pending (now 20404, as this
  item says). `store.MaxCheckAttempts` is 5 and `Verification.CheckAttempts`
  exists. The README Verify section said `VerificationCheck` was not
  emulated yet; that sentence is removed. No premise was stale.
- Twilio docs read for this item (2026-10-26):
  - https://www.twilio.com/docs/verify/api/verification-check — the
    resource fields listed in this item match; either `To` or
    `VerificationSid` must be sent; Twilio deletes a verification once
    approved, expired or out of check attempts, and a check then returns
    404. The page says nothing about a canceled verification; a check of
    one answers 20404, as this spec says.
  - https://www.twilio.com/docs/verify/api — a correct token answers
    `approved`, an incorrect one `pending`; matches.
  - https://www.twilio.com/docs/api/errors/60202 — HTTP 429, "Max (5)
    verification check attempts reached", raised on checking "more than 5
    times". So the fifth wrong check still answers `pending` and the sixth
    check gets 60202 whatever its code; the acceptance line "at the
    documented attempt" is the sixth.
  - https://www.twilio.com/docs/api/errors/60200 — HTTP 400; for a check,
    "`Code` parameter is not between 4-10 numbers long" is a cause. This item checks only
    that `Code` is present (filed as a discovered note).
  - https://www.twilio.com/docs/api/errors/20404 — not found.
- Choices the spec leaves open: a correct check also counts one check
  attempt; the check refused with 60202 is not counted, so the stored
  attempts stop at `MaxCheckAttempts`; `VerificationSid` wins when both it
  and `To` are sent; the 60200 messages are `Invalid parameter: To` (neither
  `To` nor `VerificationSid`) and `Invalid parameter: Code`; a service
  segment not starting with `VA` answers 20404, as on start; `amount` and
  `payee` are null and `sna_attempts_error_codes` is an empty list; the code
  comparison is constant-time.
- A check's `To`, when sent, must be E.164 or an email address, else
  `60200` `Invalid parameter: To`: the VerificationCheck page says "Phone
  numbers must be in E.164 format", and without the check a `To` such as
  `15550003333` matched the pending verification by its digits alone.
