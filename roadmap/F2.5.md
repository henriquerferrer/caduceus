# F2.5 — Vonage SMS API on rest.nexmo.com, through the proxy

An unmodified app calling the Vonage SMS API (`vonage.sms.send`, i.e.
`POST https://rest.nexmo.com/sms/json`) captures it in Caduceus. The Vonage
Node SDK has no base-URL env var (hosts are constructor options), so the
zero-code path is proxy mode. Node honours `HTTPS_PROXY` for `fetch` and
`http.request` only with `NODE_USE_ENV_PROXY=1`, on Node ≥24.5 (or ≥22.21)
(https://nodejs.org/api/cli.html#node_use_env_proxy1).

The SMS API always answers HTTP 200 and reports each part's outcome in the
body as string values (spec: https://developer.vonage.com/en/api/sms). The
current SDK sends a JSON body with Basic auth; the spec documents form bodies
with `api_key`/`api_secret`. Both are accepted.

## Spec
- **Surface:** a new `internal/server/vonage.go` (+ `vonage_test.go`),
  `internal/server/proxy.go` (`intercepted`), `internal/server/server.go`
  (`providerRoutes`, the listener route, `setStatus`),
  `internal/server/guard.go` (`refuse`), `e2e/vonage-node/` (new fixture
  pinning `@vonage/server-sdk`, `sms.mjs`), `e2e/e2e_test.go`, `justfile`
  (`e2e` recipe install), `README.md`. No change under `.github/`.
- **Interfaces:**
  - `intercepted` matches `rest.nexmo.com`; on it only `POST /sms/json` is
    answered and every other path passes through to Vonage (path routing).
    `POST /sms/json` is also served on the listener, for clients that set
    `restHost`.
  - Captured messages carry `Provider: "vonage-sms"`, `From` = `from`, `To` =
    `to`, `Body` = `text`, `StatusCallback` = the request's `callback`, and
    `ID` = the first part's `message-id`.
  - Until F2.7 replaces it, `setStatus` posts nothing for a `vonage-*`
    message, so a Vonage receipt URL never receives Twilio's status form.
  - The response is `{"message-count": "<n>", "messages": [...]}` with one
    entry per SMS segment (n = Caduceus's segment count), each with `to`,
    `message-id` (distinct per part), `status: "0"`, `remaining-balance`,
    `message-price`, `network`, and `client-ref` when given. All values are
    strings.
  - Errors are HTTP 200 with one entry `{"status": "<code>", "error-text": …}`:
    `2` for a missing `from`, `to`, `text`, `api_key` or `api_secret`, `3` for
    an invalid `to`.
  - `refuse` on `/sms/json` answers 403 with a problem+json body (`type`,
    `title`, `detail` naming `-allowed-hosts`), which the SDK surfaces in its
    thrown error.
- **Out of scope:** binary and WAP messages, `/sms/xml`, signature (`sig`)
  verification, delivery receipts (F2.7), the Messages API (F2.6), the Vonage
  Verify API (a later milestone).

## Acceptance
- (server test) a JSON body with Basic auth and a form body with
  `api_key`/`api_secret` are both captured and answered 200 with
  `message-count` `"1"` and `status` `"0"`; the inbox message id equals
  `messages[0].message-id`.
- (server test) a 200-character GSM body answers `message-count` `"2"` with
  two distinct `message-id`s, and the inbox holds one message with 2 segments.
- (server test) a missing `to` answers 200 with `status` `"2"` and an
  `error-text`; nothing is captured.
- (server test, test webhook server) a send with `callback` posts nothing to
  it while delivery is simulated.
- (server test, fake upstream) through the proxy, `GET
  https://rest.nexmo.com/account/get-balance` passes through to the upstream;
  `api.twilio.com` routing is unchanged.
- (server test) guard: `/sms/json` on the listener with an unknown Host, or a
  cross-site `Origin`, answers 403 problem+json naming `-allowed-hosts`.
- (server test) a `vonage-sms` capture is not a Twilio Messages resource.
- (e2e) the stock `@vonage/server-sdk` `vonage.sms.send`, run with only
  `NODE_USE_ENV_PROXY=1`, `HTTPS_PROXY`, `NO_PROXY=localhost,127.0.0.1` and
  `NODE_EXTRA_CA_CERTS`, resolves with `messages[0].status` `"0"` and a
  `message-id` that `/api/v1/wait` returns, with the code in `otp`. Twilio's
  existing `send.mjs` also passes once under that same environment. If the
  SDK cannot trust the CA this way, record it as a blocked question rather
  than changing the fixture's code.
- (README) a Vonage section, and one combined Node environment block for
  every provider: `HTTP_PROXY` and `HTTPS_PROXY`, `NODE_USE_ENV_PROXY=1`,
  `NODE_EXTRA_CA_CERTS`, `NO_PROXY=localhost,127.0.0.1`, with the Node
  version requirement and what is passed through.
