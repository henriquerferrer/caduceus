# F2.7 — Vonage delivery receipts, per request and from a default URL

Twilio captures already post status callbacks as they move from queued to
delivered. This does the same for Vonage. Most Vonage apps set their receipt
URL once in the Vonage dashboard, so besides a send's own `callback` (SMS API)
or `webhook_url` (Messages API), a new flag stands in for the dashboard
setting.

## Spec
- **Surface:** `internal/server/server.go` (`setStatus`),
  `internal/server/vonage.go`, `cmd/caduceus/main.go`, tests, `README.md`.
- **Interfaces:**
  - New option `-vonage-status-webhook` / `CADUCEUS_VONAGE_STATUS_WEBHOOK`
    (`Options.VonageStatusWebhook`). An outbound `vonage-*` message posts
    receipts to its own `StatusCallback` when set, otherwise to this URL,
    otherwise nowhere. Inbound messages never post receipts.
  - `setStatus` picks the receipt shape by provider, replacing F2.5's
    post-nothing rule. `twilio` and generic keep today's Twilio form. A
    status with no mapping posts nothing and is logged.
  - SMS API receipt: POST with a JSON body (Vonage's "POST-JSON" method)
    carrying `msisdn` (the recipient), `to` (the sender), `network-code`,
    `messageId`, `price`, `status`, `scts`, `err-code`, `api-key`,
    `message-timestamp`, and `client-ref` when given. Mapping: sent →
    `accepted`, delivered → `delivered`, failed → `failed`, undelivered →
    `expired`.
  - Messages API status: POST JSON with `message_uuid`, `to`, `from`,
    `timestamp` (ISO 8601), `status`, `channel: "sms"`, and `client_ref` when
    given. Mapping: sent → `submitted`, delivered → `delivered`, failed →
    `rejected`, undelivered → `undeliverable`.
  - Every timestamp (`scts`, `message-timestamp`, `timestamp`) comes from the
    store's clock, in UTC.
- **Out of scope:** signing receipts (Vonage's `sig` parameters and the
  Messages JWT wait for F4, like Twilio's signatures); one receipt per SMS
  part (one receipt per captured message); retries on a non-2xx answer;
  checking receipt shapes against real ones (F2.9 captures send responses
  only).

## Acceptance
- (server test, test webhook server, injected clock) a `vonage-sms` send with
  `callback` produces receipts with `status` `accepted` then `delivered`,
  carrying the send's `messageId`, `client-ref` and the injected time; a
  forced `failed` (`POST /api/v1/messages/{id}/status`) produces `failed`.
- (server test) the same for `vonage-messages` with `webhook_url`:
  `submitted`, `delivered`, and `rejected` when forced to failed.
- (server test) with `VonageStatusWebhook` set and no per-request URL, the
  receipts go to the default URL; a per-request URL wins over it; a Twilio
  message never posts to the Vonage URL; a forced status on an inbound
  Vonage message posts nothing; a forced unmapped status (e.g. `bogus`)
  posts nothing.
- (README) the option table and the delivery-simulation section describe the
  Vonage receipts and the unsigned caveat.
